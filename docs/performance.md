## 可重跑的負載對照

先啟動 `run.ps1 -NoBrowser`，確認沒有其他 Aetherpose 測試或模擬器正在執行。保留當時電源模式、CPU/GPU、其他背景負載與輸入來源。不要為了取得較好的結果刪除失敗紀錄。

```powershell
..\.venv\Scripts\python.exe tools\profile_runtime.py --seconds 8 --cycles 2 --output logs\runtime-profile-new.json
```

此命令只讀取推論服務，使用獨立暫存 Chromium 設定檔，不動使用者的瀏覽器設定。它不啟動或指派追蹤器、不改校正；輸入沿用服務目前的來源，必須另記錄為示範／模擬／實體。服務需事先啟動，輸出檔必須尚不存在。

需要重現六顆輸入的後端／頁面負載時，加 `--simulate`。此選項要求後端追蹤器清單為空，否則拒絕執行；它會暫時透過 UDP 送入六顆模擬追蹤器，結束後請後端移除並核對沒有殘留。這會暫時改變模擬裝置指派，不能在實體測試或其他模擬器運行時使用。此時輸出會標示 `six simulated UDP trackers`，不能作實體成效證據。

依序觀察沒有本次測試瀏覽器、繪圖、抑制繪圖、恢復繪圖。後三個階段會按 `--cycles` 重複；抑制繪圖僅在暫存測試頁替換 `renderer.render`，頁面的姿態接收、蒙皮、狀態更新與動畫迴圈仍持續。完成後還原方法並關閉本次建立的瀏覽器。

每階段保留逐筆服務統計。更新率由姿態版本增量除以實際觀察秒數計算，排除前兩秒；不是頁面繪圖 FPS。繪圖計數及耗時只表示 JavaScript 呼叫 `renderer.render` 的時間，不包含所有 GPU／驅動背景工作，因此不能單獨作為整台電腦的 CPU/GPU 使用率。

`backend_page_handler` 另外保存快照接收次數、接收處理時間、面板更新次數及面板處理時間；`total_cpu_ms` 是後兩者之和，立即更新時不重複計數。這包含延後執行的面板工作，避免把耗時移到計時器就誤認為負載消失。

本工具的 Chromium 明確允許 SwiftShader，實際是否使用軟體繪圖會記在 `renderer.name`；不能把軟體繪圖結果外推為所有 GPU 的效能。不同階段也可能受首次 shader 編譯、CPU 降頻、模型暖機與背景程式影響；需看重複的開／關對照，不只選最快的一段。

## 推論服務統計

`ws://127.0.0.1:9010` 的 `runtime` 包含：

| 欄位 | 定義 |
|---|---|
| `pose_fps` | 輸出姿態間隔的平滑更新率 |
| `frame_ms` | 最近一次推論循環的處理時間，不是端到端延遲 |
| `torch_threads` | 本次設定的 PyTorch 運算執行緒數 |
| `input_frames` | 輸入幀入列累計；服務重啟後重新計數 |
| `dropped_input_frames` | 待處理佇列已滿而被新輸入擠出的幀數；服務重啟後重新計數 |
| `pending_frames` | 目前仍等待處理的幀數 |
| `batch_frames` | 最近一次交給模型處理的幀數 |
| `stage_ms` | 最近一次準備、模型、CPU 複製及正向運動學耗時 |
| `model_process_cpu_ms` | 模型呼叫期間本程序所有執行緒的累計 CPU 時間，亦可能含接收與廣播工作 |
| `model_thread_cpu_ms` | 同期間呼叫模型的執行緒 CPU 時間，不含其他 PyTorch 工作執行緒 |

`input_frames` 不是實體 IMU 封包數，而是後端快照被 60 Hz 輸入流程取樣後送進模型佇列的幀數。當 `dropped_input_frames` 持續增加，代表模型未完整處理這段 60 Hz 輸入；此時即使 `LIVE 6/6`，也不能宣稱資料流沒有丟幀。計數不能直接轉換成 BLE 丟包率。

佇列目前最多保留八幀，以限制待處理積壓；本次儀表化不修改模型、門檻或排隊策略。若要調整，必須比較相同輸入下的姿態誤差與延遲，不能只追求較高 FPS。

## 面板更新策略

後端快照每次抵達時，頁面仍立即保存最新追蹤器、接收時間及頭顯新鮮度。一般封包統計、監控數值與 IK 除錯顯示合併為約 10 Hz，停止串流後也會補畫最後一筆。指派、設定、校正狀態、錄製狀態、連線及錯誤等重要變更直接更新，不等待週期。

延後顯示時，追蹤器與頭顯的資料年齡仍從原接收時間計算，不從面板繪製時間重新起算；斷線會取消尚未執行的更新。此策略只減少頁面工作，不降低後端 IMU 輸入、TransPose 推論、人體姿態接收或遊戲判定的取樣率。

合併更新後的六顆模擬量測（`logs/runtime-profile-coalesced-20261014.json`），每 8 秒面板只處理 75–78 次，快照接收仍有 458–620 次。計入接收與延後更新的總處理時間為 218–371 ms，低於先前未合併時的 974–1312 ms。不同執行時段的背景負載未完全控制，因此不將此差異直接外推成整體更新率改善。

該輪推論仍嚴重降速：無測試瀏覽器時僅 18.8 Hz，已略過 10 個輸入；後續階段約 0.2–4.9 Hz，有一次模型階段耗時約 9.7 秒。這是仍未解決的反證，不能只展示面板耗時變低就宣稱即時效能修復。接續需比較模型處理的 CPU 時間與牆鐘時間，區分實際計算、排程或等待，再處理其原因。

CPU 時間對照已記錄於 `logs/runtime-profile-cpu-clocks-20261014.json`。六顆模擬、雙執行緒的一輪中：無測試瀏覽器約 23.3 Hz，模型牆鐘中位數 37.8 ms、程序 CPU 62.5 ms；繪圖階段約 2.7 Hz，模型牆鐘 288.7 ms、程序 CPU 312.5 ms、呼叫執行緒 CPU 125 ms，分析時段略過 217 個輸入。抑制及恢復繪圖階段分別約 6.4 與 11.3 Hz，程序 CPU 中位數 171.9 與 140.6 ms。

上述程序 CPU 會累計其他執行緒，因此可超過牆鐘時間；單一執行緒時間也不是整個模型的 CPU 時間。該輪各階段都持續回報 Streaming，未觀察到推論錯誤狀態。結果不支持「只因未被排程而等待，沒有耗用 CPU」的單一解釋；也不足以區分運算量、頻率、記憶體競爭或函式庫內部等待。先前約 9.7 秒的個別停頓尚未在含 CPU 計時的這輪重現，不能宣稱已解釋該事件。

更新率計算已修正：只有「本次運算開始」與上次完成之間閒置超過一秒才重設平均；不再因本次運算本身超過一秒而排除真正的停頓。回歸同時覆蓋長推論要降低報告更新率、真正閒置後可重新建立平均。CPU 計時是觀測欄位，不改變模型權重或輸出。

## 固定輸入的 CPU 路徑比較

`tools/benchmark_cpu.py` 在獨立程序載入相同權重，以固定的六顆合成感測器輸入比較數值與耗時，不修改服務或外部模型檔。120 幀為兩秒的合成運動，不是真人驗證。每個 batch 的參考均來自相同分組的 FP32 MKLDNN；不把分組本身的差異混入後端比較。每輪先暖機八次，統計再排除前三次呼叫，第二輪反轉比較順序。

```powershell
..\.venv\Scripts\python.exe tools\benchmark_cpu.py --frames 120 --batches 3 8 --rounds 2 --backends mkldnn native --output logs\cpu-comparison-new.json
..\.venv\Scripts\python.exe tools\benchmark_cpu.py --frames 120 --batches 3 8 --rounds 2 --backends mkldnn int8 --output logs\cpu-int8-new.json
```

退出碼 0 表示比較程序完成，不表示候選通過。候選數值一致性門檻預先設為平均關節差 0.1°、最大差 1°、根位移差 0.01 m；這是對原模型的數值偏差限制，不是對真人的準確度標準。角差計算會受 FP32 矩陣正交誤差影響，相同輸出也可能有約 0.01° 的數值底限，因此同時保留矩陣元素差與位移差。

2026 年 10 月 14 日，在 PyTorch 2.11.0+cpu、oneDNN 量化引擎、兩執行緒下量測如下，欄位為每次推論呼叫耗時中位數，兩個數字依兩輪順序列出：

| 比較 | batch 3 | batch 8 | 結果 |
|---|---|---|---|
| FP32 MKLDNN | 58.7、41.4 ms | 52.4、58.5 ms | 既有路徑 |
| FP32 關閉 MKLDNN | 101.7、73.5 ms | 94.5、91.5 ms | 數值一致但更慢，未採用 |
| INT8 組內的 FP32 MKLDNN | 36.3、35.6 ms | 39.2、39.1 ms | 該組比較參考 |
| INT8 LSTM 與 Linear | 93.8、96.1 ms | 110.7、117.8 ms | 更慢且超過偏差門檻，未採用 |

INT8 平均關節差約 1.11–1.14°，最大約 5.93–6.54°，根位移最大差約 0.061–0.122 m；未進入展示服務。原始結果為 `logs/cpu-backend-comparison-20261014.json` 與 `logs/cpu-int8-comparison-20261014.json`。兩輪仍可能受背景負載影響，不能把結果推廣成所有 CPU 或所有量化引擎的結論。

API 與方法來源：[PyTorch MKLDNN 說明](https://docs.pytorch.org/docs/stable/notes/mkldnn.html)、[PyTorch 動態量化範例](https://docs.pytorch.org/tutorials/recipes/recipes/dynamic_quantization.html)。程式是否可執行以已安裝及鎖定的版本為準；量化工具是離線診斷，不是本專題提出的新模型。

## 接收端量測缺陷與修正

早期 `profile_runtime.py` 只在計時階段讀取推論資料，啟動瀏覽器及執行 CDP 操作時可能累積回壓。一輪核心配置對照因此斷線，原程序 affinity 已還原；該失敗輪不能作為有效的配置效能結論。早期報告保留為歷史觀察，吞吐率比較需以修正後的連續接收版本重新確認。

工具現以獨立非同步工作全程接收，依接收序號界定各階段並使用高解析時鐘；階段結束後仍持續讀取到關閉握手完成。中途斷線會失敗，不回傳看似正常的階段；已完成階段會留在 `completed: false` 的部分報告。`reader_mode: continuous` 可辨識新版本。新增測試驗證了計時階段外仍接收、階段不混入舊資料、正常清理及斷線失敗。

```powershell
.\run.ps1 -Restart
```

恢復預設可移除此環境變數，或設為 `1` 後重啟。只有 `0` 與 `1` 是有效值；其他值不套用提示並記錄原因。已執行的服務不會因另一個終端修改環境變數而改變，需使用 `-Restart`。`runtime.cpu_latency_policy` 會回報是否套用與原因；成功代表 API 接受提示，不保證特定更新率。

方法依據：[Microsoft SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)、[CPU Set 資訊](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-system_cpu_set_information)。四項政策測試覆蓋目前程序範圍、其他旗標保留、停用／其他平台不呼叫 API，以及讀寫失敗的回退。
